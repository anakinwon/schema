# 00. 데이터 아키텍트(DA) 팀 리더 업무계획

## ① 역할 정의

> **데이터 아키텍트(DA, Data Architect)**: 데이터 표준화 원칙 및 절차를 만들고, 모든 표준 데이터에 대한 의사결정을 하는 사람이다.
> — 데이터표준화지침서 1.4절

DA 팀 리더는 아래 세 가지 역할을 총괄한다.

| 역할 영역 | 구체적 책임 |
|-----------|-------------|
| 표준 거버넌스 | 표준화 원칙·절차 수립, 지침서 개정 승인, 예외 허용 결정 |
| 의사결정 | 모든 표준 데이터(단어·도메인·용어·코드)의 최종 승인 |
| 조직 운영 | DA팀(Data Architecture Team) 운영, 팀원 역할 배분, RACI 관리 |

## ② 참고한 지침서 및 근거

### 2-1. 데이터표준화지침서.docx 핵심 인용

**[목적 — 1.2절]**
> "데이터표준화지침서의 목적은 데이터 표준화 원칙을 수립하고 표준 데이터를 생성하여 모델 구성 요소(엔터티, 테이블, 속성, 컬럼, 속성 값)에 일관되게 사용될 수 있도록 하여 누구나 동일한 의미로 용어를 사용하고 관리할 수 있도록 하는 것이다."

이에 따라 DA 리더 업무계획의 최우선 목표는 **전사 일관성 확보**와 **표준 데이터 거버넌스 체계 구축**으로 설정한다.

**[적용 범위 — 1.3절]**
> "전사의 모든 엔터티는 데이터표준화지침서에서 정의한 원칙에 따라야 하는 표준화 대상이다. 단, 솔루션(패키지) 시스템의 스키마를 변경할 수 없을 경우에는 DA와 협의하여 속성 표준화 적용을 예외로 할 수 있다."

→ 패키지 시스템에 대한 **예외 협의 프로세스**를 Phase 0에서 사전 정의해야 한다.

**[관리 원칙 — 1.5절]**
> "표준 데이터 관리를 총괄하는 데이터 아키텍트(DA)가 반드시 존재해야 하며, DA가 소속된 부서인 DA팀(Data Architecture Team)을 운영한다."
>
> "모든 표준 데이터는 시스템을 통해 관리되어야 하며, 모든 표준 데이터의 최종 승인은 DA가 하며, 데이터표준화지침서를 근거로 승인을 한다."
>
> "데이터표준화지침서에 포함되지 않은 원칙에 대해서는 먼저 데이터표준화지침서에 포함시킨 후에 지침대로 운영한다."

→ **메타 DB(SQLite 기반 DA#5)** 를 통한 시스템 승인 워크플로우가 필수이며, 지침서 미포함 케이스 발생 시 지침서 개정이 선행되어야 한다.

**[표준화 목적 6가지 — 1.2절 상세]**
1. 의미 명확화 — 중복 정의와 불일치 제거
2. 효율적인 의사소통 — 속성 하나의 속성으로만 표현
3. 속성의 일관성 유지 — 전사 모델 일관성
4. 개발 생산성 향상 — 재사용 기회 증가, 용어 선택 시간 단축
5. 데이터 품질 향상 — 정합성 향상
6. 활용도 개선 및 업무 연계 효율 — 시스템 간 변환 부담 감소

**[표준 데이터 구성 요소 — 2.1절]**
> "데이터 표준 구성 요소는 표준 단어, 표준 도메인, 표준 용어, 표준 코드가 존재한다."
> - **표준 단어**: 명사형 최소 단위 어휘 (STD_DIC 테이블)
> - **표준 도메인**: 값의 범위·타입을 제한 (STD_DOM 테이블)
> - **표준 용어**: 표준 단어의 조합 (DA_TERM 테이블)
> - **표준 코드**: 코드 값 명을 기호화 (STD_CODE 테이블)

**[이음동의어 원칙 — 3.3절]**
> "이음동의어를 허용하면 같은 의미인데 여러 개의 표준 용어가 생성될 수 있기 때문에 이음동의어는 허용하지 않는다. 혼돈을 방지하기 위해 이음동의어를 사용하지 않도록 하는 게 표준화의 가장 커다란 목적이기 때문에 대표 단어를 표준어로 정의하고 나머지는 유사어로 등록하여 사용을 제한한다."

→ 표준 단어 등록 시 **유사어(동의어) 매핑 필수** 관리 규칙으로 DA 리더가 최종 승인한다.

### 2-2. SQLite 메타 DB 스키마가 암시하는 표준 체계

| 테이블 | 역할 | DA 리더 관리 포인트 |
|--------|------|---------------------|
| `STD_DIC` | 표준단어사전 (논리명/물리명/물리전체명) | STANDARD_YN, FORBID_YN 최종 결정 |
| `STD_DOM` | 표준도메인 (데이터타입/길이/보안등급) | SECURITY_LEVEL, PRIVACY_ACT 승인 |
| `STD_CODE` | 표준코드 (코드 ID/명/분류) | CD_GBN_CD 체계 설계 |
| `DA_TERM` | 용어사전 (다국어 포함) | TERM_GBN_CD 분류 기준 수립 |
| `STD_AREA` | 주제영역 | UP_STD_AREA_ID 계층 구조 설계 |
| `STD_DATATYPE` | DBMS별 데이터타입 매핑 | Oracle/MySQL/Impala/Netezza/Greenplum 등 지원 |

**DB 패치 이력(SQLiteDBPatch이력.txt)에서 확인된 사항:**
- 2017~2018년 사이 NETEZZA(0018), HANADB(0019), IMPALA(0023) DBMS 추가
- MySQL 전용 타입(TINYINT, MEDIUMINT, GEOMETRY 등) 확장
- `STD_DOM` 테이블에 `USE_END_DT`, `SECURITY_YN`, `KEY_DOM_PHY_NM` 컬럼 추가
- 이는 **데이터 타입 표준 범위가 다양한 DBMS를 포괄**해야 함을 의미하며, DA 리더가 DBMS 추가 시 `STD_DATATYPE_CONV` 매핑 승인 책임을 가짐

## ④ 팀원 간 의존성 및 RACI

### 팀원 역할 요약 (지침서 1.4절 기준)

| 역할 | 주요 책임 |
|------|-----------|
| **DA 리더 (DA)** | 표준화 원칙/절차 수립, 모든 표준 데이터 최종 승인, DA팀 운영 총괄 |
| **표준담당자** | 지침서 작성/관리, 표준 단어/도메인 생성, 모델러 신청 용어 검토·승인 |
| **데이터 모델러** | 표준화 지침 준수 의무, 속성 명 정의 후 표준 용어 신청 |
| **업무 개발자** | 모델러가 설계한 엔터티/속성 업무 정의 부합 여부 검토 |

### RACI 매트릭스

| 업무 항목 | DA 리더 | 표준담당자 | 모델러 | 업무 개발자 |
|-----------|---------|-----------|--------|-------------|
| 지침서 수립 | **A/R** | C | I | I |
| 표준 단어 생성 | A | **R** | I | — |
| 표준 도메인 정의 | A | **R** | I | — |
| 표준 용어 신청 | A | R (검토) | **R** (신청) | C |
| 표준 용어 최종 승인 | **A/R** | C | I | — |
| 표준 코드 관리 | A | **R** | — | C |
| 모델 업무 정의 검토 | I | — | R | **R** |
| 예외 적용 결정 | **A/R** | C | I | I |
| 지침서 개정 승인 | **A/R** | C | — | — |
| DBMS 타입 매핑 승인 | **A/R** | C | — | — |

> A = Accountable(최종책임), R = Responsible(수행책임), C = Consulted(협의), I = Informed(통보)

### 승인 워크플로우

```
모델러(표준 용어 신청)
    ↓
표준담당자(적절성 검토)
    ↓
DA 리더(최종 승인 또는 반려)
    ↓
메타 DB(SQLite DA#5) 등록 — STD_DIC / DA_TERM / STD_DOM / STD_CODE
```

> 근거: "지침서에 따른 표준 도메인과 표준 단어를 생성하며, 모델러가 신청한 표준 용어의 적절성을 검토하여 승인하는 역할을 한다." (지침서 1.4절 표준담당자 역할)
